# HTTP Request Lifecycle Documentation

## Overview

After analysis of the Core-Web framework source code, I've documented the complete HTTP request lifecycle from initial web request to final page rendering.

## Request Flow

The HTTP request lifecycle in Core-Web follows this pattern:

1. **HTTP Request** arrives at web server
2. **.htaccess rewrite rules** direct request to `webroot/index.php`
3. **`webroot/index.php`** bootstraps the framework using `Bootstrap("ROUTER")`
4. **Bootstrap process**: 
   - Starts PHP session if needed
   - Loads configuration files
   - Instantiates services based on scope (`ROUTER`)
   - Exposes services globally via `$GLOBALS`
   - Starts the active runtime dispatcher (`Router::start()`)
5. **`Router::start()`**:
   - Initializes Core helper
   - Determines requested route from URL
   - Loads and validates routes against configuration
   - Applies authorization checks
   - Renders matched route with appropriate view/template

## Detailed Flow Analysis

### Step 1: Entry Point - webroot/index.php

The entry point is `webroot/index.php`, which is generated by `CoreHelper::init()`:

```php
<?php
// Load Composer's autoloader
require_once dirname(__DIR__) . "/vendor/autoload.php";

// Initiate Bootstrap
$BOOTSTRAP = new LaswitchTech\Core\Bootstrap("ROUTER");
```

### Step 2: Bootstrap Process

The `Bootstrap` class (`src/Bootstrap.php`) handles initialization:
- Session starts if needed (for web scopes)
- Configuration loads through `Config` service  
- Services loaded based on scope map
- Services initialized and global variables set
- Router instance is started via `$ROUTER->start()`

### Step 3: Router Processing

The `Router::start()` method (`src/Router.php`) handles the actual routing:
- Calls `CoreHelper->init()` to set up environment
- Determines requested namespace from HTTP request (via `$REQUEST` service)  
- If application is installed, renders the matched route via `$this->render($this->Request->getNamespace())`
- If not installed, redirects to `/install` route

### Step 4: Route Resolution 

Route matching and rendering happens through:
- `Router::load()` - loads routes from:
  - Core error routes
  - Configured routes from `config/routes.cfg` 
  - Plugin routes from `lib/plugins/{plugin}/routes.cfg`
- `Router::set($route)` - validates authorization based on route properties
- `Router::render()` - renders matched route via `Route->render()`

### Step 5: Routing Object

The `Route` object (`src/Objects/Route.php`) handles:
- Template selection (from `Template/View/` directory)
- View file resolution
- Authorization checks 
- Actual rendering using PHP includes for template/view files

## Flow Components

### Bootstrap Services
The following services are loaded during ROUTER scope:
- UUID, REQUEST, OUTPUT, LOG, LOCALE, NET, DATABASE, SMS, SMTP
- AUTH, CSRF, STYLE, BUILDER, HELPER, MODEL, IMAP, SLS
- INSTALLER, UPDATER, ROUTER

Each service is initialized and available globally as uppercase variable names in the `$GLOBALS` array.

### Routing Authorization
Routes are checked for authorization against user permissions (using the `AUTH` service):
- Unauthenticated users get 430 "Unauthenticated"
- Unauthorized access gets 403 "Forbidden" 
- Deleted/banned users get specific errors
- Role-based permission checking via `isAuthorized('Route>' . $this->Routes[$route]->namespace(), intval($this->Routes[$route]->level()))`

## Configuration Dependencies

The routing process depends on:
- `config/bootstrap.cfg` - Bootstrap configuration 
- `config/application.cfg` - Application settings
- `config/routes.cfg` - Route definitions
- `config/auth.cfg` - Authentication parameters
- Plugin route files in `lib/plugins/{plugin}/routes.cfg`
